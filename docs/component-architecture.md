## Контракти ключових компонентів

| Компонент | Вхідні властивості | Домовленість |
|---|---|---|
| AppLayout | title, links, children | Створює спільну оболонку з одним main |
| Section | id, title, children | id унікальний у поточному документі |
| SkillList | items | Масив навичок; порожній масив допустимий |
| SkillCard | item | Коректний запис із полями моделі Л1.1 |
| StatusBadge | status | Текстовий статус, без зміни даних |
| CasePage | skill | Запис або відсутнє значення для порожнього результату |
| FormField | id, label, hint, children | Вкладене поле має відповідний id і зв'язок із підказкою |

| AppButton | children, type, variant, disabled | variant: primary або secondary |

## Обґрунтування рішень

**Чому StatusBadge замість AvailabilityBadge:** навичка має не бінарний стан (доступне/недоступне), а один із трьох текстових статусів прогресу навчання, тому компонент приймає рядок, а не логічне значення.

**Чому власні стилі, а не React Bootstrap:** наявний набір UI-компонентів (AppButton, FormField) уже має чіткий контракт і покриває поточні потреби; додавання бібліотеки зараз не усуває дублювання і не спрощує код.

**Повторне використання:** Section використано двічі з різним вмістом (композиція); StatusBadge використано в SkillCard і в CasePage без копіювання правила подання статусу.

## Стан і взаємодія (Л2.1)

### Власники стану

| Значення | Власник |
|---|---|
| `skills` (початкові дані) | модуль `data/skills.js` |
| `detailsOpen` (розгорнутий опис) | конкретна `SkillCard` (локальний стан) |
| `query`, `practicingOnly` (фільтри) | `HomePage` через хук `useSkillFilters` |
| `selectedId`, `selectedItem` (вибір навички) | `SkillSelectionProvider` (Context API) |
| `draft` (чернетка кейсу) | `CasePage` (скидається при зміні навички через `key`) |
| `visibleItems` (відфільтрований список) | похідне значення, не окремий стан |

### Чому Context API

Вибір навички потрібен одночасно двом "далеким" гілкам інтерфейсу — каталогу навичок і секції додавання кейсу. Тому замість передавання через кілька рівнів props (`App` → `HomePage`/`CasePage`) вибір винесено у `SkillSelectionProvider`, а `SkillsContainer`/`CaseContainer` читають його через власний хук `useSkillSelection`.

### useEffect

`CasePage` синхронізує заголовок вкладки браузера (`document.title`) з назвою обраної навички, із очищенням до попереднього значення при зміні залежності чи демонтуванні компонента.

## Маршрутизація (Л2.2)

### Компонування маршрутів

- `AppLayout` (шапка, підвал, `SkillSelectionProvider`, `Outlet`)
  - `HomePage`
  - `/skills`: `SkillsContainer`, `SkillDetailsPage`
  - `/cases`: `CasesLayout` (меню розділу, `CaseNotice`, `CasesGate`, `Outlet`)
    - `CasesPage`, `CaseDetailsPage`, `CaseCreatePage`, `CaseEditPage`
  - `NotFoundPage` (маршрут `*`)

### Де зберігається стан після додавання маршрутів

| Значення | Де зберігається | Після перезавантаження |
|---|---|---|
| Відкрита сторінка та її id | шлях URL | відновлюється |
| Пошук і фільтр «практикую» | query-параметри `q`, `practicing` | відновлюється |
| Навичка нового кейсу | параметр `skillId` | відновлюється |
| Останній явний вибір | `SkillSelectionProvider` | скидається |
| Текст чернетки кейсу | локальний стан `CasePage` | скидається |

### Рішення

**Провайдер вибору в `AppLayout`.** Він обгортає `Outlet`, тому вибір навички переживає переходи між сторінками, а шапка й підвал його не потребують.

**Фільтри в URL.** `useSkillFilters` читає значення з `useSearchParams`, тож окремого `useState` для них немає. Контракт хука не змінився, і `SkillsPage` та `SkillFilters` лишились без змін.

**URL важливіший за Context.** Навичку для нового кейсу та кейс для редагування визначає адреса, тому прямі посилання працюють без попередніх кліків. Context зберігає лише останній вибір як підказку.

**Спільний редактор.** `CasePage` використовується і для створення, і для редагування. Маршрутні сторінки перевіряють запис і передають йому навичку та початкові поля.


## Форми, валідація та CRUD (Л3.1)

### Власники даних

| Дані | Власник | Коли змінюються |
|---|---|---|
| Довідник навичок | модуль `data/skills.js` | не редагується |
| Колекція кейсів | `CasesProvider` | після успішного створення, оновлення або видалення |
| Чернетка кейсу | `CasePage` | під час введення; відновлюється з початкових полів |
| Ознаки `touched`, `attempted`, помилка операції | `CasePage` | після взаємодії та спроби збереження |
| Пошук, фільтр, порядок списку | URL (`q`, `skill`, `sort`) | після зміни параметрів |
| Видимі кейси | обчислення в `useCaseFilters` | з колекції та параметрів |

### Контракти операцій

| Операція | Вхід | Успіх | Відмова |
|---|---|---|---|
| `createCase` | поля кейсу | `{ ok: true, record }` | `{ ok: false, errors }` |
| `updateCase` | `id` і поля | `{ ok: true, record }` | помилки полів або відсутній запис |
| `deleteCase` | `id` | `{ ok: true }` | `{ ok: false, message }` |
| перегляд | `caseId` з маршруту | знайдений запис | NotFoundPage |

У Л3.1 ці операції були синхронними. У Л3.2 вони стали асинхронними: форма
та маршрутні сторінки очікують результат через `await`, а сама модель
результату (`{ ok, record }` / `{ ok: false, message, errors }`) збережена.
Актуальний контракт сервісу описано в розділі Л 3.2.

### Рішення

**Одна перевірка.** `validateCase` викликають `CasePage` (для показу помилок)
і сервіс через `toCaseInput` (перед записом у джерело), тому правила не
розходяться. Провайдер правил більше не знає.

**Чернетка відокремлена від колекції.** Форма працює з копією значень. Колекція
змінюється лише після успішної перевірки.

**Одна форма для створення й редагування.** `CasePage` і `CaseForm` не знають,
яка саме операція виконується: відрізняються початкові поля, `onSave` і напис
кнопки, які передають `CaseCreatePage` та `CaseEditPage`.

**Єдина процедура видалення.** Хук `useDeleteCase` запитує підтвердження з
назвою кейсу й використовується в списку та на сторінці деталей.

**Параметри списку в URL.** `useCaseFilters` відбирає, потім упорядковує
новий масив, не змінюючи колекцію.

## Л 3.2. Дані, сервіси й асинхронні операції

### Шари та відповідальність

| Шар | Файли | Відповідає за |
|---|---|---|
| Сторінки й форми | `CasePage`, `CaseCreatePage`, `CaseEditPage`, `CaseDetailsPage`, `CasesPage` | Чернетка, блокування повторного подання, перехід тільки після підтвердженого успіху |
| Провайдер | `CasesProvider`, `CasesGate` | Знімок підтверджених кейсів, стан читання (`loading` / `success` / `error`), повтор, послідовний запис (`isMutating`), захист застарілих відповідей |
| Сервіс | `caseService.js` | Єдине місце вибору джерела за `VITE_DATA_SOURCE` |
| Контракт | `caseContract.js`, `ServiceError.js` | Перевірка команд записи (`validateCase`), нормалізація прочитаних даних, коди помилок |
| Адаптери | `mockCaseService.js`, `apiCaseService.js` | Збереження й транспорт |

### Життєвий цикл даних

- **Джерело**: localStorage (ключ `daTrack.cases.v1`) або REST API. Переживає перезавантаження сторінки.
- **Знімок**: масив у `CasesProvider`. Змінюється лише після успіху сервісу, підтверджений запис застосовується з відповіді сервісу.
- **Чернетка**: стан форми в `CasePage`. Живе, доки відкрита сторінка; після відмови запису не очищується.

### Контракт операцій власної сутності Case

| Метод | Успіх | Відмова |
|---|---|---|
| `getAll({ signal })` | масив кейсів, зокрема `[]` | `ServiceError` (`STORAGE_READ`, `BAD_DATA`, `NETWORK`, `HTTP`, `MOCK_FAILURE`) або скасування |
| `getById(id, { signal })` | один кейс | `NOT_FOUND` |
| `create(input)` | повний збережений кейс із `id` | `VALIDATION`, `STORAGE_WRITE`, `NETWORK`, `HTTP` |
| `update(id, input)` | повний оновлений кейс з тим самим `id` | зокрема `NOT_FOUND` |
| `delete(id)` | `undefined` | зокрема `NOT_FOUND` |

Провайдер перетворює результат запису на `{ ok: true, record }` або `{ ok: false, message, errors, code }`.

### Рішення та межі

- Вибрано **єдиний знімок колекції** для списку, деталей і редактора. `getById` реалізовано в сервісі, але сторінками не використовується.
- Застарілі відповіді читання не застосовуються: кожне читання отримує номер версії та `AbortController`. Якщо почалося новіше читання або запис, відповідь попереднього ігнорується. Скасування зменшує зайву роботу, номер версії захищає знімок навіть тоді, коли джерело не вміє переривати запит.
- Сторінки деталей і редагування не показують «не знайдено» до завершення першого читання, бо `CasesGate` стоїть над `Outlet`.
- Відмова створення, оновлення або видалення не очищує форму й не змінює знімок.
- Одночасно виконується одна операція запису (`mutationLock`). Під час запису читання не стартує, під час читання запис не приймається.
- Автоматичного повтору запису немає: повтор міг би створити дублікат.
- Немає автоматичної синхронізації між вкладками, версій записів і виявлення конфліктів редагування. Свіжі дані читаються кнопкою «Оновити дані».
- Mock змінює тільки сховище свого origin (схема, хост, порт).
